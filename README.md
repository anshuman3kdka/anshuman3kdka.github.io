# Site Notes

This repository hosts the personal writing portfolio at [anshuman3kdka.in](https://www.anshuman3kdka.in).

Content is written in Markdown and published via Jekyll. Two generated JSON indexes support the search and random-read features on the site:

- `random-read.json` — used by the random-read button/card.
- `search-index.json` — used by the dedicated `/search/` page.

Both indexes are regenerated automatically on push (via GitHub Actions) and can be rebuilt locally with `npm run build`.

## Search system (new page-first UX)

Search lives on `/search/` as a dedicated page, keeping it simple and stable.

### Build-time search index

Search data is generated at build time by `scripts/generate-search-index.mjs`.

The script scans Markdown and HTML content files and writes compact records to `search-index.json`. Each record contains:

- `id`
- `title`
- `url`
- `category`
- `tags`
- `date`
- `excerpt`

To keep the payload small, full article bodies are not included. Token helper fields are also intentionally **not** stored in `search-index.json`.

At runtime, `assets/search-data-loader.js` normalizes the loaded data before searching:

- lowercase conversion
- punctuation stripping
- token splitting
- short/common stop-word trimming

Search data flow (high-level):

1. `scripts/generate-search-index.mjs` — scans content and writes the index
2. `search-index.json` — compact static JSON served from the site root
3. `assets/search-data-loader.js` — lazy-loads and preprocesses the index
4. `assets/search-ranker.js` — scores and sorts results
5. `assets/search-renderer.js` — renders result cards and empty states

To regenerate the index manually:

```bash
npm run generate:search-index
```

### Runtime search modules

The browser code is split into small focused files:

- `assets/search-data-loader.js` — lazy-loads `search-index.json` when the input is first focused.
- `assets/search-ranker.js` — applies lightweight scoring and sorting.
- `assets/search-renderer.js` — renders empty states and result cards; updates live region text.
- `assets/search.js` — wires page behavior (debounce, keyboard handling, result caps).

**Troubleshooting `indexUrl` / base path:**

`createSearchDataLoader()` defaults to `indexUrl: '/search-index.json'` (site root). If your site is served from a subpath (for example a project page under `/repo-name/`), pass a subpath-aware URL so the fetch points to the correct file.

### Scoring weights and behavior

Ranking priorities in `assets/search-ranker.js` (highest to lowest):

1. Exact title match
2. Prefix title match
3. Tag and category matches
4. Excerpt token matches
5. Recency (tie-breaker only)

Query behavior:

- Multi-word queries are supported.
- All-term matches receive a bonus.
- Partial and prefix matches are allowed.
- Light typo tolerance via near-prefix logic (no heavy fuzzy library).

Performance guards:

- 120 ms debounced input
- Maximum 20 rendered results
- Index lazy-loaded on first focus
- Short-query empty state: "Type at least 2 letters to search."

### Adjusting search ranking

Open `assets/search-ranker.js` and change the numeric `score += ...` values inside `rankSearchResults()`.

- Increase a value to make that match type rank higher.
- Decrease a value to make it rank lower.

After editing, regenerate the index and test at `/search/`.

## Random-read indexing

Random-read data is generated by `scripts/generate-random-read-index.mjs`.

The script scans Markdown and HTML content files and extracts the lightweight fields used by the random-read feature: `title`, `url`, `category`, `eyebrow`, and `date`. Output is written to `random-read.json`.

To regenerate:

```bash
npm run generate:random-read-index
```

`npm run build` regenerates both indexes in one step:

```bash
npm run build
```

Random-read remains independent from the search internals.

## Preventing generated index merge conflicts

`random-read.json` and `search-index.json` are generated files, so Git's line-by-line merging can produce conflicts when two branches regenerate them independently.

This repo already has a `.gitattributes` rule for `random-read.json`:

- `random-read.json merge=ours`

If `search-index.json` starts conflicting often, add a similar rule for that file.

> **Note:** GitHub's web merge flow may still show conflicts because it does not reliably apply local custom merge drivers from `.gitattributes`.

After any merge, regenerate both indexes so they match the latest content:

```bash
npm run build
```

Commit the refreshed JSON files if they changed.

## Automatic indexing on content changes

A GitHub Actions workflow (`.github/workflows/auto-update-search-index.yml`) runs automatically on pushes to `main` when content files or index scripts change. It regenerates both index files and commits the updates.

## Copy-protection behavior

Copy-protection logic is not currently active:

- `assets/site.js` does not register `initCopyProtection` handlers.
- There is no `window.initCopyProtection` export.
- `data-copy-protected` and `data-paywalled-content` attributes are currently unused by the site scripts.

If copy protection is reintroduced later, wire it explicitly in `initPage()` and document which templates opt in.

## Pages CMS media uploads

Images can be uploaded through Pages CMS and are stored in `assets/uploads/`.

- Use image fields such as **Featured Image (optional)** and **Project Image (optional)** in the editor.
- Inline images can also be added inside Markdown content using the image button.
- Uploaded files are referenced with `/assets/uploads/<filename>`.

If image uploads do not appear, verify that Pages CMS has write access to the repository branch.

## Image optimization + publishing checklist

Follow this process before publishing posts with images:

1. **Compress before uploading**
   - Use a free tool like [Squoosh](https://squoosh.app) or [TinyPNG](https://tinypng.com) to compress images before upload.
   - Target roughly **150–250 KB** for regular content images.
   - Prefer modern formats such as **WebP** when your editor supports them.
   - Avoid uploading large originals directly from a phone camera.

2. **Cloudflare optimization (if available)**
   - Enable **Polish** if your Cloudflare plan includes it.
   - Enable **Auto Minify** for **CSS, JS, and HTML** under **Speed → Optimization**.

## Additional Pages CMS configuration

The CMS provides broad editing coverage for content and site chrome:

1. **SEO fields:** collections and pages include optional `description`, `seo_title`, `og_image`, `canonical_url`, and `noindex` fields for metadata control and indexing overrides.
2. **Single-page editing:** all major page files are editable directly — `index.md`, `about`, `contact`, `resume`, `creative`, and listing pages.
3. **Site settings panel:** `_data/site.yml` controls the header title/link, nav links, footer heading/note, contact info, and social links.
4. **About portrait controls:** the about photo URL, alt text, and caption are editable through the CMS and rendered directly on the page.
5. **Home page cards:** `_data/home_cards.yml` provides repeatable cards with type, title, description, link text, and link URL fields.
6. **Featured cards section copy:** site settings include editable eyebrow, title, and subtitle text for the homepage featured cards area.
7. **Home quote rotator:** `_data/home_quote_rotator.yml` has an `enabled` toggle plus a repeatable quote list used by the homepage fade-rotating quote card.

These CMS fields are wired into the live layout:

- `<meta name="description">` uses each page's `description` when provided.
- `<title>`, `og:title`, and `twitter:title` prefer `seo_title`, then fall back to the page title and site title.
- `og:image` and `twitter:image` prefer `og_image`, then fall back to the existing social/featured image.
- `<link rel="canonical">` uses `canonical_url` when provided, otherwise uses the page URL.
- `<meta name="robots">` switches to `noindex,follow` when `noindex: true`; otherwise keeps the existing robots behavior.
- Header brand text/link and navigation read from `_data/site.yml`.
- Footer heading, text, and social links read from `_data/site.yml`.
- Homepage hero title and tagline read from `_data/site.yml`.

## Cloudflare caching checklist

After deploying content updates, use these Cloudflare settings to maximize static asset performance while keeping HTML fresh.

1. **Caching → Configuration**
   - Set **Browser Cache TTL** to at least **1 month** for static file reuse.
   - Keep **Always Online** enabled.

2. **Rules → Cache Rules**
   - Add rules for static paths and extensions:
     - `/assets/*`
     - `*.css`, `*.js`, `*.jpg`, `*.png`, `*.webp`, `*.svg`, `*.json`
   - Set **Cache eligibility** to **Eligible for cache**.
   - Set **Edge TTL** to a long duration (for example, **1 month**).

3. **HTML caching**
   - Keep HTML caching conservative unless you have a clear cache-purge workflow.
   - If you cache HTML aggressively, purge cache after every publish.

4. **Post-publish purge**
   - Use **Caching → Purge Cache** after publishing changes.
   - Use selective purges where possible; use a full purge when in doubt.

## Analytics script configuration

Analytics loading is controlled via `_data/site.yml` under the `analytics` key:

- `enabled`: `true` or `false`
- `provider`: currently `plausible`
- `domain`: your tracked domain
- `script_src`: analytics script URL

Set `enabled: true` only when you are ready to collect real traffic data.
